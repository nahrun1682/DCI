Part I

ここに至るまでの流れ

1.1　出発点：top-k スニペットという契約

背景 4本すべてが前提とする、従来のインターフェース

RAG、オープンドメイン QA、ReAct 型検索エージェント——すべて同じ契約の上に立っている。

各ターンで検索器がコーパスをランキングし、上位数件（またはそのスニペット）を返す。エージェントはそれを読んで答える。

ここでの検索の仕事は「スニペット選択」、つまりそのターンのプロンプトに収まる断片を選ぶことだ。この契約には構造的な欠陥がある。文書の関連性と、証拠としての有用性は別物だという点である。

  • 関連性の高い文書でも、決定的な事実がスニペットの切り詰めで落ちた数行に隠れていることがある
  • マルチホップでは、中間エンティティが発見されて初めてその文書の価値が判明する

つまり「適切な文書は検索できていたのに答えられない」が普通に起きる。ボトルネックは検索後の推論ではなく、インターフェースそのものにある。

読む前に — この資料に出てくるベンチマーク・指標・手法

ベンチマーク

BrowseComp-Plus（本文では BC+ とも）
ブラウジング型の難問 QA。不透明なライブ Web 検索を固定コーパス（10万文書）に置き換えることで、検索手法どうしを比較できるようにしたもの。各質問には根拠となる Gold 文書（通常 1〜4 件）と、大量のディストラクタ（無関係な妨害文書）が付く。全 830 問だが、RISE 以降は費用の都合で固定の 100 問サブセットで評価するのが慣例になっている。採点は LLM-as-a-judge（gpt-5.1）。コーパス規模の実験では、質問と Gold 文書を固定したまま、FineWeb / FineWeb-Edu（大規模な Web テキスト集合）から抽出した文書をディストラクタとして注ぎ足して水増しする。
BRIGHT
表層的な語彙・意味の一致では解けない、推論を要する検索のベンチマーク。本資料では Biology / Earth Science / Economics / Robotics の4サブセット（各コーパス 5〜12万文書、質問は各 100 問前後）。返すのは単一の答えではなくランク付きリストなので、QA とは求められる挙動が違う。
Wiki-18
2018年版 Wikipedia ダンプを使うマルチホップ QA 群（NQ / TriviaQA / Bamboogle / HotpotQA / 2Wiki / MuSiQue）。DR-DCI はこれを 2,000万個の独立ファイルとして並べ、「1ファイル1文書」の極端な設定で評価した。

評価指標

Coverage（カバレッジ）
探索の軌跡が Gold 文書にそもそも到達できたか。mean は Gold 文書全体に対する平均で、実質リコールにあたる。広さの指標。
Localization（局在化）
到達した Gold 文書の中で、どれだけ小さく実用的な範囲まで絞り込めたか。抽出したスパンが文書全体に対して短いほど高い。深さの指標。
scope recall / RG カバレッジ
いずれも RARG の分析用。前者は検索が作ったスコープ（上位1万パス）が Gold 文書を捉えている割合、後者はそのうち rg が実際にヒットしたファイルで回収できた割合。2つを分けて見ることで、劣化が検索器側か rg 側かを切り分けられる。
nDCG@10
上位10件の順位品質。ランキングタスク（BRIGHT）の評価に使う。

登場する手法・モデル

DCI-Agent-Lite
DCI 論文が用意した最小ハーネス。bash と read だけを公開し、長い探索でコンテキストが溢れないよう「切り詰め／圧縮／要約」を段階的に効かせる管理レベル L0〜L4 を持つ（L3 が既定）。RARG はこれを土台にしているので、比較が公平になる。
RISE-BM25
RISE から目次（TOC）加工を取り除いた、「境界」だけのアブレーション。RISE の2つの主張のどちらが効いているかを分離するためのもの。
RISE-Q3-Emb-4B
RISE の BM25 を密検索器に差し替えた、RARG 側が用意した対照実験。「検索器を強くすれば RISE も良くなるのでは」への回答。
Retrieval Agent / Embedding Agent
前者は RISE と一緒に公開された従来型の top-k 検索エージェント、後者は密検索で候補文書を取ってその中身を読ませるエージェント。どちらも「関連性をコンテンツとして見せる」側の代表。
NeMo Agent
候補を反復的に recall して LLM で並べ替える、NVIDIA の検索特化エージェント。重複除去を持つぶん多様な文書に届くので、「カバレッジを増やせば勝てるのか」を検証する対照として置かれている。
Q3E / NV
RARG が使う埋め込みモデルの略。Q3E = Qwen3-Embedding-4B、NV = llama-nv-embed-reasoning-3b（推論集約型で、BRIGHT 最強の NeMo が使うもの）。BC+ は全工程 Q3E、BRIGHT は文書ランキングに NV・マッチ再ランクに Q3E を使う。
バックボーン LLM
GPT-5.4 / -mini / -nano、および mimo-v2.5-pro。同じ手法でもモデル階層で順位が変わるため、複数階層で比較されている。

1.3　境界を引く

RISE 論文 対 DCI の比較値も RISE 論文が報告したもの

検索の仕事は、読む文書を選ぶことではなく、インタラクション空間を構築することだ。

インタラクション空間 = コンテキストウィンドウの外側に存在し、エージェントがシェルツールで反復探索できる、境界付きのコーパス部分集合。2つの設計帰結を実装する。

  1. 境界を検索が与える — BM25 で各サブクエリ top-K=1000 をワークスペースにハードリンク。モデルに見せるプレビューは上位10件だけで、残りは bash/read で掘らせる（search は狭いスニペット取得ではなく高リコールな文書インポート操作）

1.5　3本に共通する、見落とされていたこと

RARG 論文 ここは RARG による他3本への批判であって、3本の自己申告ではない

RISE も DR-DCI も、確かに DCI のスケール問題を解いた。だが RARG はこう指摘する。

どちらも、関連性は「探索可能な空間を構築・拡張する」ためにしか使われていない。一度インタラクションが始まってしまえば、関連性は

  • grep がどの文書から走査すべきかを指示しない
  • 大量にヒットした中で、どの抜粋がモデルに届くかを指示しない

rg はパターンに一致するだけで、すべてのファイルが同等に有望であるかのようにコーパスを舐める。ヒットは出力の切り詰めで消える。関連性という事前情報を持っているのに、探索の実行段階では捨てている。

ここが RARG の入り口である。

Part II

RARG 本体

2.1　中心主張

RARG 論文 以下 Part II はすべて RARG 論文の内容

関連性は、コーパスへの入力を選ぶだけでなく、コーパスとの相互作用そのものを導くべきである。

そのために二つの解像度の関連性が要る。

何を決めるか実装
グローバル関連性パターンマッチ操作が最初にどこを探すか文書ランキング順に逐次走査
ローカル関連性出力が観測予算を超えたとき何が表示されるかマッチ単位の再ランク

キーワードは execution prior（実行の事前情報）。関連性を「厳格な証拠のボトルネック」ではなく「実行のヒント」として使う、という発想の転換だ。

先に結論だけ。 RARG がやることは、煎じ詰めると3つしかない。

  • grep の検索対象と順番を、埋め込みの関連度順に固定する（＝ RARG）
  • 最初の grep を組み立てるための取っ掛かりの段落を渡しておく（＝ RARG+）
  • 大量に出たヒットを、一致した行そのものの関連度で並べ替えてから見せる（＝ RARG++）

以下 2.2〜2.5 でそれぞれの仕組みを見て、2.6 で実際の1問を最後まで追う。仕組みが頭に入りにくければ、先に 2.6 を読んでも構わない。

2.2　ベース構成

RARG は DCI-Agent-Lite の上にそのまま構築されている。ここは地味に重要で、新しいハーネスを作っていないので比較が公平になる。

  • ツールは Bash(command) と Read(doc_path, offset, limit) のみ
  • コンテキスト管理は DCI のレベル3（ツール結果の切り詰め + 古いターンの [cleared] 置換）
  • コーパス全体への ls/find は禁止（停止するため）
  • rg の返すマッチ数は BC+ で30件、BRIGHT で60件に制限、各マッチは1,000/500文字に切り詰め
    → 出力は最大でも約30,000文字で、DCI の 50KB を大きく下回る

2.3　レベル1：文書レベル関連性の注入（= RARG）

課題

「関連性で文書を並べる最も普通の方法」＝上位文書を LLM に直接食わせる、は素の grep に負けることが DCI で示されている。だから検索を証拠チャネルそのものにしてはいけない。

解法：embed_recall

新ツール embed_recall(scope_query) を追加する。ただし——

文書の中身は一切返さない。
ランク付けされた文書パスの一覧を /tmp/scope_N.txt に書き出し、LLM には「/tmp/scope_N.txt → クエリ」というマッピングだけを返す。

そして LLM にはこう指示する。

cat /tmp/scope_N.txt | xargs -d '\n' rg -j1 [OPTIONS] "PATTERN"

これでスコープ内の全パスが rg に指定順で渡され、関連度の高い文書から順にマッチが出てくる。

細部が効いている

設計理由
-j1rg はデフォルトで並列読み込みし、スレッドの完了順にマッチを出力するのでパス順が壊れる。シングルスレッドを強制する（実装は rg 呼び出しを正規表現で捕まえて -j1 を注入）
スコープ上位1万パス全部書いてもコストが増えるだけ。1万件でも scope recall 95〜97% を維持できる（＝Gold はほぼ取りこぼさない）
圧縮時も scope を保持LLM が常に利用可能なスコープを把握できるように

これで文書レベルの関連性が「top-k コンテンツの選択」ではなく「検索順序」へ変換される。

2.4　レベル2：エントリポイント初期化（= RARG+）

エージェントは質問文しか持っておらず、embed_recall は中身を返さない。だから rg が良い取っ掛かりを見つけるまで数ステップ無駄にする。

追加の LLM ターンを使わずにそれを与えるため、スコープ上位文書を 400〜1000 文字の段落に分割 → 埋め込みでスコープクエリに対しスコアリング → 上位10段落を <qr_paragraph> タグで embed_recall の出力に添える。

これは答えではなく、最初の精密検索を組み立てるための出発点。圧縮時にはクリアされる。

2.5　レベル3：マッチレベル関連性の注入（= RARG++）

課題

文書レベルの関連性だけを見ると、有益な抜粋が「周囲の文書に希釈されて順位が低い文書」の中にあると、切り詰めで見えなくなる。

解法

rg のマッチ候補を広めのプール（M=500）で取り、埋め込みで再ランクして上位 m 件（30〜60）だけ提示する。再ランク用のクエリをどう作るかが肝で、グローバルな目標とローカルな意図の両方を捉える必要がある。

案作り方精度
構築クエリ
（採用）		Instruct: … Query: [スコープクエリ] RG focus: [キーワード1] [キーワード2]…
スコープクエリ（大域目標）と rg パターンから機械的に取り出したキーワード（局所意図）を連結		84%
生成クエリBash を RerankAwareBash(command, rerank_query) に置き換え、LLM に再ランククエリを書かせる75%
誠実な考察

生成クエリが負けた理由を、著者は train-test gap に帰している。明示的な再ランククエリを出力させると、学習時に身につけた Bash/rg の挙動が乱れる。ただし収束は最速（17.8ツール）なので、このギャップを埋めるのは今後の課題、としている。

核心の一行は 202 番目にある。エージェントには届かない。だから別のパターンを試し、また全走査し……を繰り返す。DCI が 1問あたり 99.1 回もツールを呼ぶのはこれが理由。

② RARG は、まず走査順を決める

RARG — 1ターン目
> embed_recall("mathematician AMS fellow 1983 PhD coauthor Peres Pemantle")

  /tmp/scope_1.txt を作成 → クエリ: "mathematician AMS fellow ..."

返ってきたのはこれだけ。文書の中身は1文字も返らない。作られたファイルの中身は、関連度順に並んだパスの一覧である。

/tmp/scope_1.txt
1.     doc_00082.txt      ← 関連度 1位
2.     doc_04417.txt
3.     doc_00214.txt
        :
10000. doc_25150.txt      ← ここまでで Gold の 95〜97% を捕捉

そのうえでさっきと同じパターンで grep を打つ。変わるのは対象と順序だけ。

RARG — 2ターン目
$ cat /tmp/scope_1.txt | xargs -d '\n' rg -j1 -n "American Mathematical Society"

cat … | xargs で検索対象がスコープ1万件だけになり（10万件の全走査ではない）、-j1 で並列をやめてscope_1.txt に書いた順に走査する。結果——

エージェントが実際に見る出力
  1  doc_00082.txt:216: ...Fellow of the AMS (2012), Ph.D. 1983...     ← 本命が1番目
  2  doc_04417.txt: 41: ...joint work with Peres and Pemantle...
  3  doc_00214.txt: 12: ...(関連はするが決め手ではない)
        :
 30  doc_03119.txt: 77: ...(無関係)
──────────── ここで出力が切れる ────────────

同じパターン、同じコーパス、同じ切り詰め。変えたのは順番だけ。それで本命が可視領域に入る。これが「関連性を実行の事前情報として使う」の中身である。

③ RARG+ が足すもの — 最初の一手を捨てない

何に困っているのか

②で走査順は直った。しかし打つパターンそのものは、まだ質問文から推測するしかない。ここに grep 特有の落とし穴がある。

grep はリテラル一致である。質問文の言い回しと、コーパス側の書き方が一致している保証はどこにもない。

RARG（初期化なし）— 質問文の語をそのまま投げるとこうなる
$ cat /tmp/scope_1.txt | xargs -d '\n' rg -j1 "AMS Fellow"
  → ほぼ当たらない。コーパスは「Fellow of the American Mathematical Society」と書いている

$ cat /tmp/scope_1.txt | xargs -d '\n' rg -j1 "R. Pemantle"
  → 参考文献欄ばかり当たる。本文の表記は「Robin Pemantle」

エージェントはコーパスがどう書いているかを知らないままパターンを投げている。走査順が正しくても、パターンが当たらなければ前に進まない。素の RARG がこの問題で7ターン目まで答えの文書に届かなかったのがこれである。

どう作るか

解決策は素朴で、「コーパスの実物を少しだけ先に見せる」。ただし追加の LLM ターンは使わない。embed_recall の応答に相乗りさせる。

  1. スコープ上位の文書を 400〜1000 文字の段落に切る
  2. 各段落を埋め込みでエンコードし、スコープクエリに対してスコアリング
  3. 上位 10 段落だけ残す
  4. <qr_paragraph> で囲み、embed_recall の戻り値の末尾に付ける
embed_recall の戻り値に追加される部分
<qr_paragraph>
  ...was elected a Fellow of the American Mathematical Society in 2012,
  following joint work with Yuval Peres and Robin Pemantle on random walks...
</qr_paragraph>

これでコーパスが実際にどう書いているかが分かる。エージェントは表記をそのまま写して撃てる。

RARG+ — 1ターン目からこう打てる
$ cat /tmp/scope_1.txt | xargs -d '\n' rg -j1 "Robin Pemantle"
  → 共著者チェーンに直行

「とりあえず AMS で探ってみるか」という探りの一手が丸ごと消える。論文のケーススタディでは、答えを含む CV の初出が 7ターン目 → 2ターン目、ツール呼び出しが 33 → 18 回に落ちている。

当然出る疑問 — 主張と矛盾しないのか

「関連性をコンテンツとして見せるな」が RARG の主張なのに、ここでは文書の中身を見せている。矛盾に見えるが、設計は3点で一貫している。

  • 量 — 10 段落だけ。top-k 検索のように候補を丸ごと流し込むのとは桁が違う
  • 役割 — 答えの根拠ではなく、次の grep を組み立てるための材料。事実の確認はあくまで本文を read して行う
  • 寿命 — コンテキスト圧縮時にクリアされる。証拠として蓄積されない。だから「証拠チャネル」にはならない

④ RARG++ が足すもの — 順位の低い文書の一行を救う

何に困っているのか

②で本命が1位に来たのは、本命の文書がたまたま関連度1位だったからである。現実にはこうならない。

文書順だけだと起きること
関連度    1位  doc_00311.txt  長い伝記記事
              → "American Mathematical Society" に 10件ヒット、全部ただの言及
関連度 4000位  doc_00082.txt  短い CV
              → ヒットは 1件だけ。しかしそれが「Fellow of the AMS (2012)」

文書レベルの順序で並べると、上位文書の凡庸なヒットが表示枠を食い尽くす。長い文書ほどヒット数が多いので、これは構造的に起きる。

着眼点：rg の出力は「文書」ではなく「行」の列である

rg が吐く1件の単位
doc_00311.txt:1042: ...presented at the American Mathematical Society meeting...
└── パス ──┘└行番号┘└──── 一致行とその周辺（最大1,000文字） ────┘

1件ずつが独立した短い断片である。ということは、文書のスコアとは無関係に、断片そのものを評価して並べ替えられる。これが RARG++ の着眼点。

具体的には、rg のヒットを最大 M = 500 件プールし、断片を埋め込みでスコアリングして上位 m 件（BC+ は30、BRIGHT は60）だけを提示する。ヒットが m 件に満たなければ再ランクはスキップされる。

肝は「再ランク用のクエリをどう作るか」

ここが一番わかりにくいところ。断片を並べ替えるには基準となるクエリが要るが、手元にある2つのどちらか片方では足りない。

本資料片方だけでは足りない理由
使うもの捉えているものそれだけだと
スコープクエリ大域の目標
「1983年博士・Peres/Pemantle 共著の AMS フェロー」		いま何を探して grep を打ったのかが反映されない
rg のパターン局所の意図
「American Mathematical Society」		その語を含む行なら何でも上位に来る。元の目的を見失う

だから両方を機械的に連結する。これが「構築クエリ」。

再ランククエリ（構築クエリ）
Instruct: ...
Query: mathematician AMS fellow 1983 PhD coauthor Peres Pemantle   ← 大域（スコープクエリ）
RG focus: American Mathematical Society                            ← 局所（rg パターン由来）

rg のパターンはルールに従ってキーワード列に変換され、スコープクエリの後ろに連結される。LLM は一切介在しない。

結果として何が起きるか

再ランク前 — 文書順（500件）
  1-10  doc_00311.txt  関連度1位の伝記から、凡庸な言及が10件。枠を独占
        :
  417   doc_00082.txt:216: ...Fellow of the AMS (2012), Ph.D. 1983...
        :
──────── 上位30件で切ると 417番は消える ────────
再ランク後 — 一致行の関連度順（上位30件）
  1  doc_00082.txt:216: ...Fellow of the AMS (2012), Ph.D. 1983...   ← 417位から浮上
  2  doc_00311.txt:1042: ...(伝記の言及。1件だけ残る)
  3  doc_04417.txt: 41: ...joint work with Peres and Pemantle...

関連度4,000位の文書の一行が、先頭に来る。文書スコアでは絶対に届かない位置にある証拠を、断片単位の評価で拾い上げている。

3.4 の分析とつながる

これが「3変種の中で RARG++ のヒット分布が最も平坦（＝下位ランクからも回収している）」の正体である。大域の関連性が走査順を決め、局所の関連性が可視性を決めるという2段構えが、この一例に両方出ている。

逆に言うと、この「絞り込み」が裏目に出る場面もある。幅広く候補を集めることが求められるランキングタスク（BRIGHT）では、RARG++ は3変種で最下位になる。詳しくは 3.3 を参照。

⑤ 3変種を並べると

RARG 論文ケーススタディ — 同一問題での軌跡
手法ツール呼び出しターン答えを含む CV の初出結果

3つとも同じ答え（Russell David Lyons）にたどり着いている。変わったのは正解したかどうかではなく、そこに至る手数である。粗い関連性（走査順）→ 出発点の付与 → 細かい関連性（一致行の可視性）と足すたびに、収束が速くなっていく。

(e) 対照実験も効いている。 RISE の BM25 を同じ埋め込みに差し替えた RISE-Q3-Emb-4B は 69% とむしろ悪化。RISE は BM25 インターフェースに適合しており、強い密検索器を挿せば良くなるものではない。

→ 「スケーラビリティの結論はディストラクタの作り方に依存する」という、この分野全体への警告になっている。

3.3　BRIGHT（推論重視の検索）：順位が逆転する

本資料 ここまでとタスクの形そのものが変わるので、先に何が違うかを整理する

そもそも 3.1 / 3.2 と何が違うのか

3.1 と 3.2 は BrowseComp-Plus、つまり QA だった。エージェントは最後に「Russell David Lyons」のような答えの文字列を1つ出し、それが合っているかで採点される。

3.3 の BRIGHT は ランキング（IR）である。エージェントは答えを出さない。クエリに対して関連しそうな文書を順位付きリストで返すのが仕事で、その並べ方の良さを測られる。

本資料タスクの形の違い
3.1 / 3.2 — BrowseComp-Plus3.3 — BRIGHT
タスクQA（質問に答える）ランキング（関連文書を並べる）
エージェントの出力答えの文字列 1つ順位付きの文書リスト
採点正解率（LLM-as-a-judge）nDCG@10（上位10件の順位品質）
勝ち方検証済みの経路が1本通ればいい
→ 深さ優先		関連文書を取りこぼさず並べる必要がある
→ 幅優先
速く収束することそのまま得（手数もコストも減る）必ずしも得ではない。早く打ち切ると候補を取りこぼす

「推論重視」とは何か

従来の検索ベンチマーク（BEIR など）では、クエリと正解文書に語の重なりがある。「フランスの首都」に対して正解文書には「フランスの首都はパリである」と書いてある。だから BM25 でも埋め込みでも、そこそこ当たる。

BRIGHT はそうなっていない。クエリは実際の質問投稿で、正解文書はその質問に答えるために必要な文書。両者は語彙も表層の意味も重ならないことが多い。

本資料 — 性格を示すための作例

たとえば「ロボットアームのこの振動がどうしても消えないのはなぜか」という質問に対し、必要な文書には「振動」も「ロボット」も出てこず、制御理論の減衰比についての一般的な説明だけが書いてある、という具合になる。「この原理を当てはめれば説明がつく」と考えて初めて、関連していると分かる。

だから BM25 のような語彙一致は特に弱く（表3 で RISE-BM25 が 41.60 と最下位なのはこれ）、素朴な埋め込みでも足りない。BRIGHT で強いのは、RARG が使う NV のような推論集約型の埋め込みモデルと、LLM に関連性を考えさせる手法である。

要するに BRIGHT は、「関連性を判定すること自体が難しい」うえに「広く集めて正しく並べる」ことを要求する。QA 向けに最適化した速い収束が、そのまま得になるとは限らない。実際そうなる。

QA では RARG++ > RARG+ > RARG だったのが、ここでは RARG+ > RARG > RARG++ と反転する。上で見たタスクの形の違いが、そのまま効いている。

  • ランキングは幅優先 — 関連文書をできるだけ多く回収してから並べる → RARG++ の「観測リソースを局所的に優れた抜粋へ集中させる」性質が裏目に出る

関連性ガイダンスの最適な粒度は、タスクが「速い収束」を求めるか「広いリコール」を求めるかで変わる。

3.4　挙動分析：メカニズムが意図通りか

ヒットのランク分布（スコープ順位のどこで関連文書に当たるか）

エージェントプロファイル解釈
Embedding Agent上位に鋭く集中、ただし総ヒット数が少ないtop-k が冗長な文書を返し、同じ情報に観測予算を浪費
NeMo Agent重複除去でより多様、だが関連性＝コンテンツの枠内インターフェースの制約は同じ

RARG++3変種中最も平坦、下位ランクからも回収マッチレベル再ランクが、低スコア文書に埋もれた抜粋を引き上げている

→ 設計（大域＝走査順、局所＝可視性）が意図通りに機能していることの直接的な証拠。

Bash の内訳

mini では 96〜98% が「スコープ付き rg」。nano では 87.5% まで落ちるが、これはメカニズムの限界ではなく指示追従の弱さ（nano は embed_recall の呼び出し回数も 9〜14 回と多く不規則）。

ケーススタディ

数学者を AMS フェローシップ・博士号取得年・共著者2名から特定する問題。3変種とも正解（Russell David Lyons）だが、ツール 33 → 18 → 10 回、ターン 17 → 11 → 10 回と厳密に減少。答えを含む CV の初出は RARG では7ターン目、初期化ありの2変種では2ターン目だった。

Part IV

評価

4.1　良いところ

本資料 ここから 4.2 までは論文の主張ではなく、紹介者の評価

  1. 主張と実装が一対一に対応している。「大域関連性＝走査順」「局所関連性＝可視性」の2軸が、そのまま -j1 逐次走査とマッチ再ランクという2つの実装になり、そのままアブレーション（RARG / + / ++）になり、そのままヒット分布の図で検証されている。論文としての骨格が非常にきれい。
  2. DCI-Agent-Lite をそのまま使っているので、改善がインターフェース由来だと言い切れる。
  3. -j1 の話が実務的に面白い。「rg は並列だから出力順が壊れる」という、実装者しか気づかない事実が主張の成否を握っている。
  4. ネガティブ結果を消していない。生成クエリ版が悪化したこと、BRIGHT で RARG++ が最下位になること、100万文書で劣化することを全部報告している。

4.2　気になるところ・突っ込みどころ

本資料

論点中身
埋め込みモデル依存文書ランキング（長文の評価）とマッチ再ランク（短い抜粋の評価）は別の能力を要求する。実際 BRIGHT では NV が短いマッチで信頼できず Q3E にフォールバックしている。「十分に強い埋め込みモデル＋それに適合したハーネス」への依存は、DCI が捨てたはずのもの
レイテンシ-j1 の強制と再ランクは検索を遅くする。並列実行後に並べ替える手もあるはずで、性能と時間のトレードオフは残る（定量値は論文に出ていない）
RISE との矛盾スケーリングの結論が真逆。ディストラクタが長文か短文かで変わる、という説明は妥当だが、どちらが「正しい」評価設定なのかは未解決
評価規模BC+ は100クエリのみ、judge は GPT-5.1 単一。数ポイント差は方向性として読むべき
比較の非対称性DCI 側は 50KB の出力を許すのに RARG は 30KB に絞っている。切り詰め方が違う条件下でのツール数比較なので、「効率」の比較には注意が要る

4.3　位置づけまとめ

本資料 4本を横断して整理したもの

本資料4本の設計空間
候補集合の境界空間内オブジェクト関連性の役割検証したスケール
DCIなし（コーパス全体）生テキスト使わない20万で崩壊開始
RISE静的（BM25 top-K）TOC 挿入済空間の構築100万で安定
DR-DCI動的（pull で拡張）生テキスト空間の構築・拡張1,000万〜2,000万
RARG実質なし（順序付け）生テキスト走査順＋観測可視性100万で緩やかに低下

議論は最終的に 「境界を引くか（RISE / DR-DCI）」 vs 「境界は引かず優先順位だけ与えるか（RARG）」 に収束している。そして4本すべてに共通する結論はひとつ。

エージェント型検索の性能は、検索器の品質だけでは決まらない。「コーパスをどの解像度で、どういう順序で、どこまで見せるか」というインターフェース設計が、同じかそれ以上に効く。

Part V

想定質疑

本資料 発表時に出そうな質問と、論文から返せる答え

結局これは BM25 で絞ってから grep するのと何が違うのか？

絞っていない。スコープは1万件（コーパスの10%）で、中身は返さず順序だけ渡す。RISE-BM25（絞る）との差 84 vs 77 がその答え。

なぜ埋め込みの上位文書をそのまま読ませないのか？

それが Embedding Agent（55%）と NeMo（64%）。DCI が示した通り、関連性をコンテンツとして見せた瞬間に解像度を失う。

-j1 はどれくらい遅いのか？

論文は「実験では許容範囲」としか書いていない。定量値は出ていない（限界として明記されている）。

RISE の「スケールしても劣化しない」と矛盾するが？

ディストラクタが FineWeb-Edu の長文か否かで結論が変わる。RARG 側は scope recall は落ちず RG カバレッジだけ落ちることを示して、劣化源が検索器ではなく rg の局所マッチだと特定している。
